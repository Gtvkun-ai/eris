## 1. Decisions

D1. **Own worker thread inside `LivingUserMemoryService`**, not the digest-kernel worker. `BackgroundMemoryDigestKernelService` is a single thread that also drops jobs older than 240 s (`skip_if_older_seconds`); parking it on a 2-minute Gemini call is how digest jobs go stale. A dedicated daemon thread `ERIS-LivingUserEpisode` follows the `MemoryGCService` pattern (daemon thread + `threading.Event`). Started lazily on the first request, so tests that never request consolidation start no thread.

D2. **Snapshot / outside / commit-by-id.** Under `_turn_buffer_lock`: copy rows. Release. Call Gemini. Persist the episode (`episode_store.add`, already atomic via `atomic_write_json`). Re-take the lock briefly and remove only the snapshot's row ids (minus the `keep_tail` tail). Rows that arrived during the call are untouched. Order is strictly: persist episode, then trim buffer.

D3. **No fallback on ordinary Gemini failure.** Matches "ko co thi khoi sai summary". The worker calls the builder in strict mode: a failed/timed-out/empty Gemini result raises, the buffer stays, a retry is scheduled with backoff. Exceptions: (a) `model_adapter is None` (Gemini disabled): heuristic episode immediately, as today; (b) buffer pressure: when the buffer holds >= 40 rows (hard cap is 48 and older rows are silently dropped by `[-48:]`), persist the heuristic episode so nothing is lost. The heuristic episode keeps `metadata["source_turns"]`.

D4. **What chat uses when the new summary is not ready** (verified against the readers): chat reads only (i) `episode_store.all()` / `recent()` (`capture_interpretation_context`, `compile_context`, `episode_prompt_view`), (ii) the rollup recap via `EpisodeRollupStore.render` (returns `""` if its coverage hash is stale), and (iii) up to 12 raw recent turns from the in-memory buffer (`build_evidence_context`). Therefore "not ready" == the most recent previously persisted episodes/recap, or nothing if none exist, plus the raw recent turns. Nothing waits for the worker and nothing is changed on the reader side beyond a bounded lock acquire. `episode_store.add` merges into the existing same-session episode, so a finished summary replaces the older one atomically.

D5. **Hard timeout in two layers.** (i) The adapter call gets `timeout` (`ERIS_LIVING_USER_EPISODE_TIMEOUT_SEC`, default 60) and the `_LANE_LOCK` acquire is bounded by the same budget. (ii) The worker runs the build in a helper daemon thread and joins with `timeout + 5 s`, so a misbehaving adapter (like the 5-10 s sleeping fake) cannot hold the worker. On timeout the helper's late result is discarded.

D6. **Single flight + retry.** `_cons_run_lock` (non-blocking acquire) guarantees one consolidation at a time (worker and the legacy sync `flush_session`). Backoff `min(600, 60 * 2**(failures-1))` s (`ERIS_LIVING_USER_EPISODE_RETRY_SEC` base). State is in memory; durable state is the persisted buffer plus the `living_user_trace.jsonl` events. After an app restart the leftover buffer is picked up by the next `record_conversation_turn` session change or the next `dream()`.

D7. **Defer while a user turn is active.** Worker polls every 5 s and skips the run while `GLOBAL_INFERENCE_BROKER.user_turn_active()` is true (lazy import in `try/except`, overridable attribute for tests). This is not a failure and does not count toward backoff.

D8. **`MemoryKernel.maintain()` keeps calling `rollup_episodes()` and `dream()` inline** (a docs file and `test_episode_fading.py` pin that). `dream()` only stops flushing inline; it requests consolidation instead. Residual: rollup + the dream's profile-ops Gemini call still occupy the digest worker thread (no chat lock involved). Report it, do not fix it here.

D9. **OCR: one switch, `ERIS_SCREEN_OCR_ENABLED`, default OFF** (new `src/screen/ocr_config.py::screen_ocr_enabled()`, read at call time). OFF means: no backend probe, no `rapidocr_onnxruntime`/`pytesseract` import, no pip self-heal, `should_ocr=False` in every capture, `refresh_now` never forces OCR. UIA text, window title and the cheap change detector stay (UIA is not OCR; the detector feeds `changed_ratio`). Setting `ERIS_SCREEN_OCR_ENABLED=1` restores today's behaviour.

D10. **Vision replaces OCR for explicit screen references on the same turn.** Today, with no usable text evidence the router returns `mode="vision", needs_visual=False`, and `prepare_turn` then queues vision for the NEXT turn (`ocr_needs_next_turn_vision`). With OCR gone that would delay every "nhin man hinh di" by a turn. So, when OCR is off, `ScreenRelevanceRouter.route` returns `needs_visual=True` in its "no usable text evidence -> vision" and "not strong enough -> vision" branches if the reference is explicit (`not resolution.inherited`) or a direct-vision marker matched. Pure anaphora (inherited) keeps the existing next-turn queue. `prepare_turn` already captures immediately when `mode=="vision" and needs_visual`.

D11. Accent-folding false positives (`screen_anaphora_rescue.py` anchors `anh`/`code`, deictics `no`/`do`/`day`; `intention_authority.py` `mo`) are NOT fixed. The verification script measures what they now cost (section 3, check 5) and the report gives a one-line suggestion.

## 5. Why `episode_rollup status=failed error=ValueError` happens

`EpisodeRollupStore.run` (`episode_rollup.py`) catches every exception, sets `_retry_at = now + 300 s` and returns `{"status":"failed","error":type(exc).__name__,"reason":getattr(exc,"status","")}`. `ValueError` can only come from: `_validate` (`invalid_rollup_segments`, `invalid_rollup_segment`, `rollup_budget_exceeded`: Gemini returned segments with an anchor outside `allowed_anchors`, duplicate anchors, empty text, more than 8 segments, or too many tokens), or `_load` (`invalid_episode_rollup_store`, or `json.JSONDecodeError`, which subclasses `ValueError`, for a corrupt `living_user_episode_rollups.json`). `CuratorInferenceError` is a `RuntimeError`, so the transport failures seen that evening (3x `CuratorInferenceError`) would have printed a different name. Conclusion: most likely Gemini returned structurally invalid segments during a flaky period; this is by-design validation plus a 300 s retry, not a code bug.
